# SuperPatient

一个长期记录自己检查检验指标的追踪系统，适合体检、慢病随访这类需要**持续对比同一指标**的场景。

核心不是「录入数值 + 折线图」，而是把**非结构化化验单照片**变成**可比较、可追踪的结构化指标**。

> 演示与开发均使用合成数据，不含任何真实个人健康信息。

## 核心链路

```
拍照上传
   │
   ▼
POST /api/files/upload      图片落盘 + 登记归属（仅上传者本人可读）
   │
   ▼
POST /api/parse/report      多模态模型抽取 → JSON → 归一化 → 候选值（不落库）
   │
   ▼
校对页（人在环路）            逐项核对、修正、丢弃；模型不直接写库
   │
   ▼
POST /api/records           结构化入库，参考区间随值快照保存
   │
   ▼
趋势图 + 分段参考区间带 + 异常标红
```

关键取舍：模型只产出**候选**，落库必须经过用户确认。既能追问准确率，又不由模型承担责任。

## 功能

| 模块 | 说明 |
|------|------|
| 账号 | 用户名 + 密码注册/登录，BCrypt 存储，JWT 鉴权 |
| 记录 | 按分类录入检查记录，数值型/文本型指标，自动判定偏高偏低 |
| 识别 | 上传化验单照片 → 模型抽取 → 校对页确认 → 入库 |
| 趋势 | 单个指标多次复查折线，参考区间按每次报告分段绘制 |
| 指标管理 | 公共指标只读，自己的指标随便改；别名（用于抽取归一）与性别/年龄参考区间规则 |
| 随访提醒 | 按你自己的历史复查间隔推算待办；连续异常提前、结果恢复自动关闭 |
| AI 解读 | 记录详情页生成解读。深读模式下模型自己决定查哪些数据（工具调用），不可用时降级为规则摘要 |
| 调用记录 | 每次解读的轮数、工具链、token、耗时都留痕，可在「调用记录」页展开查看轨迹 |
| 关注指标 | 标星长期关心的指标，录入页默认展开、趋势页可只看这些 |
| 图片 | 报告照片按上传者鉴权访问，不走公开静态目录 |

## 技术栈

- 后端：Spring Boot 4 / Java 21 / MyBatis / MySQL 8 / JWT
- Web：Vue 3 + Element Plus + ECharts（Vite 构建）
- 抽取：可插拔多模态客户端，`mock`（默认，无需 Key）/ 通义千问 VL
- 密码：`spring-security-crypto` 的 BCrypt（未引入完整 Spring Security）

## 快速开始

**环境**：JDK 21、Maven 3.9+、MySQL 8、Node 18+

### 1. 初始化数据库

首次初始化会 **DROP 并重建全部表**：

```bash
mysql -uroot -p --default-character-set=utf8mb4 < schema.sql
```

`schema.sql` 已包含全部表结构与种子数据（7 张表：user / exam_category / exam_indicator / exam_record / exam_value / reference_range / upload_file），**不需要再执行 `db/` 下的迁移脚本** —— 那些只用于升级已有库。

可选：导入合成演示数据（6 次血常规、两家医院、参考区间不同），用于演示趋势页的分段参考带：

```bash
mysql -uroot -p --default-character-set=utf8mb4 super_patient < db/demo_trend_data.sql
```

### 2. 本地配置

数据库密码不写在仓库里。复制模板并填入：

```bash
cp backend/application-local.yml.example backend/application-local.yml
```

```yaml
spring:
  datasource:
    username: root
    password: 你的数据库密码
```

`application-local.yml` 已被 `.gitignore` 排除。也可以用环境变量 `DB_USERNAME` / `DB_PASSWORD` 覆盖。

### 3. 启动

```bash
cd backend && mvn spring-boot:run        # http://localhost:8080
cd frontend/Web && npm install && npm run dev   # http://localhost:3000
```

打开 `http://localhost:3000`：

| 账号 | 密码 | 用途 |
|------|------|------|
| `demo` | `demo1234` | 基础示例数据 |
| `demo_trend` | `demo1234` | 6 次复查的趋势演示（需先导入 demo 数据） |

也可以点「注册」创建新账号，注册时需选择性别（用于匹配参考区间）。

### 4. 切换真实模型

默认 `LLM_PROVIDER=mock`，返回固定样本，用于无 Key 时打通链路。

```bash
export LLM_PROVIDER=qwen
export DASHSCOPE_API_KEY=sk-xxx
# 可选：LLM_MODEL / LLM_BASE_URL
```

### 5. 可选：启动 AI 解读的 Agent 服务

```bash
python agent/server.py --port 8001     # 仅需标准库，无第三方依赖
export AGENT_ENABLED=true              # 后端启动前设置
```

不启动也能用——解读会自动降级为规则摘要。

## 备份与恢复

两样东西要一起备份：**数据库**和**报告照片**。只备份数据库会得到一堆指向不存在文件的记录。

```bash
# 1) 数据库（结构 + 数据，含中文，必须指定字符集）
mysqldump -uroot -p --default-character-set=utf8mb4 \
  --single-transaction super_patient > backup/super_patient-$(date +%F).sql

# 2) 图片：默认落在 backend/uploads（可用 UPLOAD_DIR 覆盖）
tar -czf backup/uploads-$(date +%F).tar.gz -C backend uploads
```

恢复到一个空库：

```bash
mysql -uroot -p -e "CREATE DATABASE super_patient CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci"
mysql -uroot -p --default-character-set=utf8mb4 super_patient < backup/super_patient-2026-10-25.sql
tar -xzf backup/uploads-2026-10-25.tar.gz -C backend
```

三个注意点：

- `--default-character-set=utf8mb4` 不能省，否则中文指标名会变成 `???`
- `--single-transaction` 避免备份时锁表（InnoDB 下不阻塞写入）
- **备份文件含真实健康数据**，不要提交进仓库，也不要放到公开网盘

## 几个设计点

**用户即患者本人。** 一个账号就是一份健康档案：性别、出生日期直接挂在 `user` 上，检查记录用 `user_id` 外键。没有"账号→患者→记录"的中间层，归属校验也就退化成一次字段比较。

**参考区间分三级，而不是一个全局常量。** 判定顺序：

```
报告照片上印的区间 (exam_value.ref_*)   ← 最可信，落库时快照
        ↓ 没有
性别/年龄规则命中 (reference_range)      ← 规则表，按 priority → 具体度 → 区间窄度排序
        ↓ 没有
指标默认值 (exam_indicator.normal_*)     ← 兜底，不写快照，便于以后调整
```

同一指标在不同医院、性别、年龄段区间都不同，做成全局字段就表达不了。落库时用 `ref_source` 记录本次用的是哪种来源。

**抽取分三层，便于评测。** `LlmVisionClient` 只返回模型原始 JSON；schema 校验、别名归一、单位换算都在后处理层。这样才能把 prompt 优化、schema 约束、后处理规则拆开做对照实验。

**单位换算连参考区间一起换。** 只换数值不换区间，异常判定会整体错位。

**人在环路。** 模型输出只是候选，用户逐项确认后才写库。低置信度、别名匹配、单位换算都会在校对页标出来。

**指标库分两层，公共只读。** `exam_indicator.owner_id = 0` 是系统维护的公共字典（血常规、尿常规、影像文本项），所有人可见但不可改；用户新增的指标归属自己，只有创建者能看见、能改。所有查询共用一句可见性谓词 `status = 1 AND (owner_id = 0 OR owner_id = #{userId})`，包括抽取候选池——漏一处的后果是 A 的私有指标出现在 B 的下拉里。

这样设计是因为化验单的写法无法穷举：真实样本里出现的「平均RBC体积」「全血C反应蛋白」「PLT分布宽度」都不在标准名里。公共库只保留跨医院通用、区间稳定的项，长尾交给用户自己长出来；同分类下不允许重名，否则候选池里会出现两个同名指标、匹配结果不确定。

当前公共库保留 34 项：血常规 22（白细胞/红细胞/血小板三大系细分）、尿常规 3、影像文本 9。生化 33 项已 `status = 0` 停用——它们仍属于历史记录，只是不再出现在录入页和抽取候选里，需要时由用户自己新增。

**图片不走静态目录。** `GET /api/files/{id}` 校验上传者归属，非本人返回 404 不泄露存在性；鉴权支持请求头或 `?token=`（`<img>` 无法带请求头）。

## 抽取评测

用 8 张真实化验单截图（4 家医院、模板各不相同）跑端到端评测：模型 `qwen3-vl-plus`，人工逐行标注 196 行作为基准，`eval/` 下三个脚本分别负责标注草稿、批量抽取、比对出报告。

| 样本 | 标注行 | 召回 | 数值 | 单位 | 归一化 | 误报 |
|---|---|---|---|---|---|---|
| 01 | 22 | 100% | 100% | 100% | 100% | 0 |
| 02 | 43 | 100% | 100% | 100% | 69.8% | 0 |
| 03 | 21 | 100% | 100% | 100% | 100% | 0 |
| 04 | 19 | 100% | 100% | 100% | 94.7% | 0 |
| 05 | 23 | 100% | 100% | 100% | 100% | 0 |
| 06 | 23 | 100% | 100% | 100% | 95.7% | 0 |
| 07 | 24 | 100% | **75.0%** | 100% | **58.3%** | 0 |
| 08 | 21 | 100% | 100% | 100% | 100% | 0 |
| **合计** | **196** | **100%** | **96.9%** | **100%** | **87.2%** | **0** |

- 召回 100%、误报 0：报告上没有的没被编出来，有的也没被漏掉。单位同样全对，包括 `10^9/L`、`%`、`g/L` 这些易混写法
- 数值 96.9%，6 处错**全落在样本 07**（新医院），而且不是随机错，是**末位截断**：`33.7→33`、`340→34`、`13.7→13`、`9.5→9`、`20.5→20`、`0.01→0.0`。同一张图另一半行的小数位却是准的，说明不是整图裁切，更像该院模板让末位数字难以辨认
- 归一化 87.2%：24 行抽到了但归不进指标库，集中在 MCV/MCH/MCHC 的中英混排写法（`平均RBC体积`）、嗜酸/嗜碱粒细胞计数、各类分布宽度。属于**指标库覆盖**问题，补别名即可，与识图能力无关
- 值与单位挤在一个字段（`167 g/L`）时按「数字 + 剩余文本」拆分；未匹配到指标库的行同样拆，否则单位和值会整块丢掉
- 同一张样本连跑 3 次结果完全一致；行更密的那张曾出现漏 3 行的波动，所以校对页不能省
- 模型与提示词只负责「看见什么」，schema 校验、别名归一、单位换算全在后处理层，改一层不会污染另一层

结论：召回和单位已经打满，剩下的错误集中在**新模板的末位数字**和**别名覆盖**。前者靠人在环路兜（校对页标可疑），后者靠补指标库。

补完这批公共别名后重测 06/07：归一化 95.7% → **100%**、58.3% → **95.8%**，只剩「大血小板比率」这一项指标库里确实没有，走校对页的「加入我的指标」建档。同时 07 的数值准确在这两轮之间从 75% 回到 95.8%——说明那 6 处「末位截断」更像**单轮偶发**而非稳定的模板缺陷。单张样本的数值表现波动很大，样本量不够时不该据此下结论。

指标口径（召回 / 数值 / 单位 / 归一化怎么算）见 [eval/README.md](eval/README.md)。

## AI 解读：一个能自己取数的 Agent

记录详情页的「AI 解读」有两个模式，区别不在 prompt，而在**模型有没有工具**：

| 模式 | 数据来源 | 调用次数 | 实测耗时 | 定位 |
|---|---|---|---|---|
| **深读（agent）** | 模型自己调工具取数 | 1-6 次工具 + 生成 | 2-8s | **默认路径** |
| 快速（simple） | Java 组装好的证据包 | 1 次生成 | ~7s | 兜底：服务不可用或成本敏感时 |

agent 模式只拿到 `recordId` 和问题，可用五个只读工具：`find_indicator` / `list_records` / `get_record` / `get_trend` / `get_reference_rules`。每次调用都留痕到 `insight_log`（问题、轮数、工具次数、token、耗时、是否降级），可用 `GET /api/insights/logs` 回看。同一份代码，问法不同路径就不同：

```
「这次有哪些指标超出参考区间」→ get_record                      2 轮 3.3s
「我的血糖最近怎么样」        → find_indicator → get_record
                                → get_trend(id=6, limit=2)     4 轮 6.3s
「看看甘油三酯」              → get_record（发现未检测，直接说明） 2 轮 2.1s
```

### 对照实验：30 个问题 × 两种模式

`python eval/run_agent_eval.py`，30 个问题覆盖异常项、单指标取值、跨记录对比、缺失指标、影像记录，以及「下不下诊断」的边界问题。事实命中按「答案里是否出现预期数值/结论、且不含越界表述」判定：

| 模式 | 事实命中 | 平均耗时 | 平均工具调用 | 平均 token |
|---|---|---|---|---|
| 快速（证据包） | **17/30（57%）** | 6.4s | 0 | 925 |
| 深读（工具调用） | **30/30（100%）** | 4.5s | 1.6 | 3225 |

两个反直觉的结果：

- **证据包模式的失败不是"不知道"，是"答非所问"**：它每次都把整包数据总结一遍，问"血红蛋白正常吗""白细胞是多少"都给出同一段摘要。没有工具、没有目标，模型只能复述输入
- **agent 反而更快**：证据包每次要灌 1k token 的上下文并生成长答案，agent 只发小 prompt、按需取数
- **第一轮只有 27/30，暴露的是工具缺口**：问「上次检查是什么时候」时模型手上只有 get_record / get_trend，跨记录问题答不了；补了 list_records 才到 30/30

**护栏**：最大 6 轮 / 20 秒；相同工具参数重复调用直接回 error 逼它换策略；**一次工具都没调就想作答 = 编数据，直接拒绝并降级**；命中「建议/治疗/用药/剂量/确诊」的内容整条丢弃；免责声明由 Java 拼接，模型无权生成。

**按题型统计**：每次调用会用关键词规则打一个题型标签（异常概览 / 趋势对比 / 跨记录 / 单指标取值 / 总体概括 / 越界提问），「调用记录」页按题型聚合条数、平均轮数、token、耗时、降级次数。跑 120 条测试问题的结果：趋势对比 28 条、平均 2.3 轮 2810 token（最贵），异常概览 20 条只要 1.5 轮 1543 token。**哪类问题贵，一目了然**。

**quick 只做兜底**：证据包模式（simple）没有工具，问「血红蛋白是多少」「上次是什么时候」都会退化成复述全量数据（见下方对照实验：17/30）。因此后端默认走 agent，simple 仅保留给「Agent 服务不可用」或成本敏感的场景。

**降级**：Python 服务没启动或超时 → Java 用规则拼摘要（“本次共 6 项，其中 2 项超出参考区间”），功能不依赖模型。Agent 服务细节见 [agent/README.md](agent/README.md)。

## 已知限制

- 仅 Web 端，无移动端
- Token 无刷新与吊销机制，12 小时到期后需重新登录
- 登录接口无验证码与限流，注册开放，仅适合自用或演示
- 参考区间规则只覆盖差异明确的几项（血红蛋白、尿酸、肌酐、血沉、碱性磷酸酶、白细胞），其余走指标默认值
- 趋势图的参考带按每次报告区间分段；只有一个数据点的指标看不出阶梯变化
- 评测集只有 8 张截图、196 行，覆盖 4 家医院的血常规与生化，专科报告与外文报告还没测
- 指标库没覆盖的项（生化、专科项、eGFR 等）能抽到但归不进去：校对页可以为它一键建成自己的私有指标，也可以手动指定已有指标
- 公共库只保留血常规/尿常规/影像文本，生化项要靠用户自己建；后续若做「模板包一键载入」再补
- 停用指标只影响「以后还能不能选」：录入页看不到，但历史详情、趋势、统计照旧可读
- 无审计日志与数据导出权限控制
